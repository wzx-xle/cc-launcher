## Context

`ccl serve` 周期性地向各 provider 的额度接口发请求。请求的调度由三件事决定：**哪些池要刷**（活跃判定 + 保鲜阈值）、**什么时候刷**（相位错开 + 到期判定）、**刷多快**（轮内最小间隔 + 429 退避）。

Windows 主环境的日志（`serve.log`，7 个池、ticker 8 秒一轮、周期 60 秒）显示：

```
16:09:09 provider iflytek-jlcao3 被厂商限流（HTTP 429），退避 1m0s 后再试
16:10:13 provider iflytek-jlcao3 被厂商限流（HTTP 429），退避 2m0s 后再试
...
14:43:02 provider iflytek-xjxiang 被厂商限流（HTTP 429），退避 1m0s 后再试
14:43:10 provider iflytek-jlcao3  被厂商限流（HTTP 429），退避 1m0s 后再试   ← 隔 8 秒
```

其余 5 个池（minimax × 3、deepseek × 2）3 小时零 429。

## Goals / Non-Goals

**Goals:**

- 同一厂商（endpoint）的两个额度池，相邻请求间隔不小于 `vendor_gap`（默认 10 秒），**跨轮也成立**。
- 一个池被 429 → 同厂商的其它池一起暂停（不再"一个退避、另一个照打照限"）。
- 换 key 后不被旧退避挡住。
- 退避能真正爬到封顶（一次成功只降一级，不是清零）。

**Non-Goals:**

- 不改"哪些池要刷"（活跃判定、保鲜阈值）—— 那部分工作正常（日志证明 7 个池各自 60 秒一次）。
- 不改轮内 500ms 的最小间隔（那是跨厂商的通用下限，保留）。
- 不做厂商侧的请求合并（同厂商同账号的多个 key 合并成一个请求）—— 需要厂商配合，超出本 change。
- 不动额度数据的语义与展示口径。

## Decisions

### D1: 厂商间隔用"endpoint"作为分组键，且跨轮生效

**决策**：新增 `EndpointThrottle`，按 endpoint 记录"上次请求时刻"，发请求前若距上次同 endpoint 请求不足 `vendor_gap` 就等待。节流器由 **daemon 持有**（跨轮复用）。

**理由**：日志证明两个讯飞池的 429 时刻只隔 8-20 秒 —— 它们**不在同一轮**（相位相隔 8 秒），所以轮内 500ms 间隔完全管不到。相位错开解决的是"不要挤在同一时刻"，但厂商的限流阈值是**时间窗口内的请求数**，不是"同一时刻"。所以约束必须跨轮、且按厂商分组。

**为什么分组键是 endpoint 而不是池**：池 = endpoint + key 哈希。用池分组 = 现状 = 两个讯飞池互不约束（问题照旧）。用 endpoint 分组 = 同厂商所有 key 一起受约束 ✓

**为什么默认 10 秒**：日志里 8-20 秒的间隔触发了限流 → 约束必须大于这个量级；10 秒是保守取值，且远小于 60 秒周期（不会显著拖慢刷新）。**可按 provider 覆盖**（`quota.vendor_gap`）—— 某个厂商特别严格时，用户可以把它调大。

**跨轮为什么需要 daemon 持有状态**：节流状态若只在单轮内有效，跨轮相邻的两次请求（相位相隔 8 秒）就管不住 —— 而这正是日志里的实际形态。daemon 是常驻进程，内存里存"每个 endpoint 的上次请求时刻"即可（无上限，池数个条目）。

**`ccl quota --refresh` 怎么办**：一次性进程，没有历史 → 首次请求不等待。这与它"用户主动要求立刻拿数据"的语义一致；真被限了会拿到 429 并写入退避（退避是持久化的 → 后续 daemon 也会退避 ✓）。

### D2: 退避按厂商记，同时保留池级

**决策**：429 时**同时**写两条退避：厂商级（endpoint 键）与池级（池键）。判定时**任一**命中就跳过。

**理由**：厂商级解决"同厂商不同 key 一起限"（日志实证）；池级解决"同 key 多 provider 共用一把 key，厂商按 key 限"（现状正确，保留）。两者是**或**关系 → 任一维度被限都暂停。

**为什么不是"只按厂商"**：如果厂商真的按 key 限流（不同 key 不受影响），按厂商记会让一个 key 被限时**所有** key 都停 —— 过度保守。只按厂商则无法覆盖"同 key 多 provider"的情况（那本来就同池，池级已覆盖 → 其实只按厂商也够）。

嗯，这里要想清楚：**同 key 多 provider = 同池 = 池级退避已覆盖** → 厂商级退避**只**影响"同厂商不同 key"。

那"只按厂商"是否就够？是的，逻辑上覆盖了两种情况。但"只按厂商"会让"换 key"也被挡（直到 30 分钟封顶）→ 所以 D3 的 key 指纹豁免是必要的。

**结论**：厂商级 + 池级都记（AND 判定：两个都到期才查）比"只按厂商"更保守也更精确 —— 但复杂度更高。

简化决策：**只按厂商记退避 + key 指纹豁免**（D3）。理由：
- 同 key 多 provider = 同池 = 同 endpoint → 厂商级退避**同样**覆盖 ✓（不需要单独的池级）
- 换 key 的豁免由 key 指纹实现（D3）
- 少一套键 = 少一处可能出错

⚠️ 但这改变了现有 spec 的 "a replaced key is not held back" 语义（那条现在只在池级成立）→ 必须 MODIFIED spec。

### D3: 退避按接口记，换 key 也不豁免（取舍：厂商整体保护 > 换 key 即时可用）

**决策**：退避记在 endpoint 上；**同接口的所有额度池一起暂停**，provider 换 key 后**仍**受该退避约束。

**理由（来自日志）**：讯飞的**两个不同 key** 的 provider 被同时限流 → 厂商限的是**账号/出口 IP**，不是 key。此时"换 key 就豁免"是**错的**（换了也躲不掉），而"同厂商一起停"是**对的**（账号级限流下，继续打只会让限流更严重）。

**为什么不豁免**："换 key 即时可用"与"同厂商一起暂停"在逻辑上**不可兼得** —— 退避记录在接口级时，无法区分"这个池换了 key"与"同接口的另一个 key"。二者必选其一，日志证据指向后者。

**代价（如实记）**：用户换 key 后最多要等一次退避（首次 1 分钟）。退避"成功一次降一级而非清零"让这个等待不会无限拉长。

**key 指纹**：仍记录在退避条目里，但**只用于诊断日志**（"这次被限的是哪把 key"），不用于豁免。

### D4: 退避在一次成功后降一级，而不是清零

**决策**：成功刷新时，把该厂商的退避时长**减半**（下限为初始值 1 分钟），而不是直接删除。

**理由**：日志显示 13:59 已退避 4m，14:24 又从 1m 开始 —— 中间一次成功把退避清零了。而讯飞的限流是**速率型**的：刚成功一次不代表可以立刻恢复高频请求。清零让退避永远爬不起来 → 反复撞 429。减半则让退避在持续成功时缓慢恢复（4m → 2m → 1m → 无），在持续失败时快速爬升（1m→2m→4m→8m→16m→30m 封顶）。

**退避到期后的自然恢复**：到期后第一次请求若成功 → 减半（而不是清零）→ 仍有一级退避残留 → 下次失败又从 1 分钟级继续。符合"速率型限流"的直觉。

## Risks / Trade-offs

- **[厂商间隔会拖慢一轮刷新]** → 一轮里若有 N 个同厂商的池同时到期，耗时增加 N×(vendor_gap - 现有间隔)。7 个池 / 60 秒周期 / 10 秒间隔 → 最坏一轮多花约 20 秒。daemon 是后台常驻，不影响用户交互。

- **[换 key 豁免可能让厂商继续被撞]** → 用户换 key 后立刻发请求，厂商若真的按账号限流（换 key 换账号则不冲突）→ 风险取决于厂商的限流维度。豁免只影响"换 key 的那个池"，同厂商其它池仍受保护。

- **[退避减半而非清零 → 一次偶发成功后会留一级退避]** → 用户手动 `ccl quota --refresh` 可能撞上残留的退避而被拒。缓解：手动刷新路径对"厂商级退避"也遵守（这是既有语义："The wait applies to an on-demand refresh as well"）。

- **[退避记录的键变了 → 旧的池级退避记录失效]** → 升级后第一次可能多撞一次 429。可接受（退避本来就是临时状态）。

- **[节流器状态只在内存里]** → daemon 重启后丢失 → 重启后第一轮可能同厂商连发两个。缓解：daemon 启动时立即刷一轮 → 那一刻还没有历史 → 不等待。可接受（重启是低频事件）。

## Migration Plan

1. `quota.json` 的 `backoffs` 键格式变更：旧键（64 位十六进制池哈希）读不出 → 视为无退避。无需迁移脚本。
2. `quota` 配置新增可选键 `vendor_gap`（毫秒）；不配置 → 默认 10 秒。
3. 无回滚需求（旧版二进制读新格式的 backoffs 会读不出 → 视为无退避）。
