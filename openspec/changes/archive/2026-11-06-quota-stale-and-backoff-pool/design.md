## Context

### 缺陷 1 的算术

```
fetched_at = floor(T_fetch)          // Unix 秒精度
age(now)   = now − floor(T_fetch)
           = (now − T_fetch) + frac(T_fetch)
                └── 真实年龄 ──┘   └── ≤ 1 秒的取整误差 ──┘
```

而真实年龄的峰值（刷新前一刻）≈ `周期 − 刷新耗时`（刷新是在"该刷新的时刻"
**之后**才完成的：HTTP 请求 + 文件写入）。于是：

```
age 峰值 ≈ 周期 − 刷新耗时 + 取整误差(≤1s)
```

阈值取"正好等于周期"时，只要刷新耗时 < 1 秒，这个峰值就会越过阈值 → 稳态下
每次刷新前约 1 秒误报。

实测数据（42 秒亚秒精度采样）：峰值 60.75~61.48 秒 → 越线 4~8 次。

### 缺陷 2 的语义错位

| 概念 | 粒度 | 归属 |
|---|---|---|
| 限流 | **key**（厂商针对那把 key 限流） | 额度池 = (端点, key) |
| provider | 文件名 | 一个 provider 引用一个池 |
| 退避状态 | 现在挂在 provider 名上 | ❌ 错位 |

一个 provider 的 key 换了 → 池变了 → 厂商那边是**另一把 key** 的限流额度 →
老退避不该拦住它。

## Decisions

### 决策 1：stale 阈值 = refreshInterval + 1 秒

**为什么是 1 秒**：取整误差的上界恰是 1 秒（`frac < 1`），而刷新耗时恒 > 0
→ 真实年龄峰值恒 < 周期 + 1 秒 → 阈值取 `周期 + 1s` 能**完全**覆盖，不会引入
新的误报窗口。

**为什么不是别的**：
- `1.1 × 周期`：6 秒的容忍对 10 秒周期来说太宽（数据真旧了 6 秒才报 stale）
- `周期 + 刷新耗时估计`：多一个需要维护的量，且不精确
- 存毫秒精度的 `fetched_at`：改数据格式的成本远大于收益

**语义不变**：stale 依然是"数据比刷新周期还旧"，只是不再被取整误差误伤。

### 决策 2：退避按额度池（pool）记录

数据文件新增顶层段：

```jsonc
{
  "version": 1,
  "entries": { "p1": { "source": "...", "pool": "3f2a9c…", "fetched_at": …, "next_at": … } },
  "backoffs": {
    "3f2a9c…": { "retry_after": 1793956332, "seconds": 60 }
  }
}
```

- key = pool 哈希（`sha256(端点 + "\0" + API key)`）——**与额度本身的分池口径
  完全一致**（限流是针对 key 的，额度也是按 key 分的）
- 一个 pool 被多个 provider 引用时只记一份 → 不会出现"同一个池，一半退避一半
  没退避"的分裂状态
- 换 key = 换池 → 老退避自动不适用 ✓

### 决策 3：老数据文件的退避状态惰性迁移

v0.20.1 把退避写在条目里（`retry_after` / `backoff_seconds`）。读文件时做一次
**惰性迁移**：条目有退避且条目知道自己属于哪个 pool（`entry.Pool`）→ 并入
`backoffs[pool]`。

- 不丢退避（升级后不用重新挨一次限流）
- 迁移只在读时做，写回时自然变成新格式 → **一次性自愈**
- 条目没有 `pool` 字段（极老的数据文件）→ 丢弃该退避（无害：会被重新限流并
  重新记录）

### 决策 4：`--refresh` 的退避检查也查 pool

命令层要先算出 pool（`Resolve()` 拿端点 → `PoolID`）→ 查 `backoffs[pool]`。
`Resolve()` 失败（没有额度接口）的情况在更早的分支就返回退出码 2 了，不会走到
这里。

## Risks / Trade-offs

- **老版本 ccl 读新数据文件**：不认识 `backoffs` 段 → 忽略 → 退避失效（会多打
  一次被限流的接口）→ 无害
- **新版本 ccl 读老数据文件**：惰性迁移 → 退避不丢 ✓
- **`backoffs` 段会无限增长**：每个池一条；池的个数 = provider 数 × 端点数，
  有界（`Prune` 只清 entries 不清 backoffs → 可以顺手清掉没有对应 provider 的
  池，但收益不大，先不做）
